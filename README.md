# SRAL LIMS

Internal Laboratory Information Management System for **Sadguru Research & Analysis
Laboratory**, Kolkata. Lives at **sral.foodtesting.com**, separate from the public website
(foodwatertesting.com) and from Prachar (erp.foodwatertesting.com) — different domain,
different logins, same lab, same Supabase project.

- **Hosting:** a dedicated Cloudflare Worker (`sral-lims`), static SPA + security headers, no
  server-side routes. Built from this repository by Cloudflare Workers Builds on every push
  to `main` (once you connect the repo — see **Deploy**, below).
- **Database:** the same Supabase project as the public website and Prachar (project `SRAL`,
  `jbuhflpfapdhwpgnpbkm`), in its own schema, `lims`. Nothing is shared between schemas except
  the project — see `supabase/migrations/20261003090100_lims_02_security.sql` for the full
  access model.
- **Accounts:** completely separate from the public website (which has no logins at all) and
  from Prachar (its own `prachar.*` staff table). A LIMS login only ever grants `lims` access.

## What v1 covers

Sample accessioning → test assignment → results entry → review and approval (segregation of
duties enforced: whoever entered a result cannot also approve it, unless they're an admin) →
Certificate of Analysis, plus a client registry, user/role administration and a full audit
trail. See **Module scope** below for what was deliberately left for a later version.

## Module scope (v1)

Approved for this first build: **sample accessioning, test assignment, results entry,
review & approval, Certificate of Analysis, user/role management, audit trail.** A real LIMS
can grow a lot more modules — reagent/consumable inventory, instrument calibration tracking,
a client-facing portal, billing, document control, non-conformance tracking. None of those are
built here; the schema and RLS model (`lims.has_role()`, the `lims.staff_role` enum, the
audit-log pattern) are written so adding a module later means a new migration and a new page,
not a redesign.

## How the database access model works

Every table in `lims` has row-level security enabled and denies everything by default.
Reads are open to any active, signed-in staff member (`lims.current_role() is not null`);
**every write goes through a `SECURITY DEFINER` function** — `accession_sample`,
`assign_analyst`, `enter_result`, `review_result`, `issue_certificate`, `set_staff_role`, etc.
— never a direct table insert/update from the browser. Each of those functions:

1. Checks the caller's role itself (not just RLS), so error messages can explain exactly what
   went wrong ("Only a reviewer or admin can review a result"), not just a bare permission denial.
2. Enforces the sample/test state machine (you can't review a result that hasn't been entered,
   issue a certificate before every result is approved, etc).
3. Writes its own row to `lims.audit_log` — so the audit trail can never be skipped by a bug
   in a screen; it's guaranteed at the database layer.

The very first person ever to sign in becomes `admin` automatically (a one-time trigger that
only fires when `lims.staff_profile` is empty). Everyone after that starts as `pending` — no
access to anything — until an existing admin sets their role from the **Users** screen.

## Keys (what's secret and what isn't)

`build/config.json` holds the Supabase **publishable** key (`sb_publishable_...`). This is
meant to be public — Supabase's own documentation is explicit that this key is safe to ship to
a browser, the same way the public website and Prachar already do. It grants nothing by
itself; every permission check happens in Postgres via the RLS policies above. **Nothing in
this repository needs a secret, a service-role key, or an environment variable.**

## Deploy

1. **Apply the database migrations** (not yet done as of this commit — see below).
2. **Connect this repository to a new Cloudflare Worker.** In the Cloudflare dashboard:
   Workers & Pages → Create → Workers Builds → connect `AIAkshar007/SRAL`, branch `main`.
   - Build command: `node build/build.mjs`
   - Deploy command: `npx wrangler deploy`
   - Root directory: `/` (this repo's root — `wrangler.jsonc` is already here)
3. **Point `sral.foodtesting.com` at the Worker.** Add the domain under the Worker's
   Settings → Domains & Routes → Add → Custom Domain. If `foodtesting.com` is not yet on
   Cloudflare's nameservers, add it as a Cloudflare zone first; Cloudflare will then manage the
   DNS record for the subdomain automatically when you add the custom domain.
4. **Create the first login.** In the Supabase dashboard for project `SRAL` → Authentication →
   Users → Add user. Use the lab's real email and set a password (or use "Send magic link" if
   you'd rather the first admin set their own). The first person to actually sign in at
   `sral.foodtesting.com` with that account becomes admin automatically — nothing else to
   configure.
5. **Add everyone else from inside the app**, not the Supabase dashboard: once an admin is
   signed in, open **Users**. New staff still need their login created in the Supabase
   dashboard the same way (Authentication → Users → Add user) — there's no self-service sign-up
   by design, this is a closed internal tool — but after that first sign-in, the admin sets
   their role and activates them from the LIMS itself.

### Applying the migrations

The four files in `supabase/migrations/` need to be run, in order, against the `SRAL` Supabase
project. **They were written and fully tested against a local Postgres 16 instance (schema,
security, every workflow function exercised end-to-end, including the "analyst can't review
their own result" rule) before this commit**, but **were not yet applied to the live project**
when this was built — the project was paused (see below) and out of reach at the time.

To apply them, either:
- **Supabase SQL Editor** (simplest): paste each file's contents, in filename order
  (`01_schema`, `02_security`, `03_functions`, `04_seed`), and run.
- **Supabase CLI**: `supabase db push` from this repository, with the project linked.

### A live-project problem to know about

The `SRAL` Supabase project (the one behind foodwatertesting.com, Prachar, **and** this LIMS)
is currently **paused** — Supabase's free-tier projects auto-pause after a period with no
activity, and this organization already has two other active free projects
(`klsharma`, `akshar-asin-command-center`), which is the free-tier limit. That blocks
restoring SRAL without pausing one of those two, or upgrading the organization's plan.

**This affects more than the LIMS: the public enquiry form on foodwatertesting.com and Prachar
are also unreachable while SRAL stays paused.** Resuming it (Supabase dashboard → the SRAL
project → "Restore project", or pausing one of the other two first) is worth doing regardless
of this LIMS.

## Local development

```
node build/build.mjs        # builds app/src/ into dist/
node -m http.server 8080 -d dist   # or any static file server — it's a plain SPA
node worker/test/worker-test.mjs   # Worker behaviour checks (headers, SPA fallback, CSP)
```

There's no bundler, no `npm install`, no framework — plain HTML/CSS/JS, matching the house
style of `foodwatertesting-website` and Prachar in the sibling repository.

## Testing notes (for whoever picks this up next)

The database layer (all four migrations, the full sample lifecycle — accession → assign →
enter → review → approve → issue certificate — plus the segregation-of-duties rule and every
role-gate) was exercised against a real local Postgres 16 instance, not just read for syntax.
The UI (every screen, every form, the Enter Result / Review / Add Client modals, and the
Certificate of Analysis PDF — including Unicode text, since Helvetica/WinAnsiEncoding doesn't
have glyphs for curly quotes, em dashes or subscript digits by default) was exercised in a
real headless browser against a mocked backend, not just read. The Worker's security headers,
CSP, SPA fallback and robots.txt were checked by running the actual `worker/index.js`, not a
stand-in. None of this reached the live Supabase project — it was paused throughout, and no
test data was ever written to it.
